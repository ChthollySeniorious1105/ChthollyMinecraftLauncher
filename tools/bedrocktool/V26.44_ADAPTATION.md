# BedrockTool — Minecraft Bedrock 26.44 适配说明

> 历史记录：当前工作区已升级到 26.52，请参阅 [V26.52_ADAPTATION.md](V26.52_ADAPTATION.md)。

本工作树基于用户提供的 `bedrocktool-master` 源码，目标客户端版本为 Minecraft Bedrock 26.44。

## 版本基线

- Minecraft 版本：`1.26.44`
- 网络协议：`2168`
- Gophertunnel 协议基线：Sandertv/gophertunnel `v1.59.0`（commit `4794743`）
- Go 工具链：Go `1.27.0` / Windows amd64
- 行为包内容格式：`1.26.40`（26.44 是基于 26.40 的热修复版本）

BedrockTool 使用的 Gophertunnel、Dragonfly 和 go-raknet 都包含 fork 专用 API，因此没有整包替换为上游 master。适配保留了这些 API，只同步目标版本所需的协议编解码、注册表和调用点。

## 主要改动

1. 将 Gophertunnel 的 `minecraft/protocol` 固定到 `v1.59.0`：
   - `CurrentVersion = "1.26.44"`
   - `CurrentProtocol = 2168`
   - 使用 2168 的 Cereal variant/Optional 编解码
   - Scoreboard remove entry 使用双层 Optional 编码
2. 由于 Mojang 在 26.44 改了线格式却没有更换协议号，监听端会检查登录中的游戏版本；26.40–26.43 只有在配置了对应旧协议转换器时才接受，否则明确拒绝，避免用 26.44 布局误解码。
3. 适配 PlayerList、MoveActorDelta、地图、LevelChunk/SubChunk、blob cache、皮肤颜色与手臂尺寸等新结构和 Optional 字段。
4. 升级 `go-nethernet` 到 `v1.0.20`，使用带 Context 的 signaling API 和 cancel cause 传递关闭/服务端错误；源码包内保留本地模块，以承载 26.44 所需的最小连接就绪修复。
5. 修复 26.44 资源包下载：兼容 `UUID_version`、每块立即 Flush、200ms 可取消节流，并按实际偏移判断末块。
6. 保留 olebeck Dragonfly fork 的区块、MCDB、未知方块和自定义物品 API；同步 26.44 方块/物品注册表，并适配其 session 层的配方、输入、清单、记分板与子区块调用。
7. 修复 `utils/merge` 中 `go:linkname` 的函数 ABI 不匹配，并增加实际执行哈希函数的回归测试。
8. 生成的实体与自定义方块行为包改用 `format_version: 1.26.40`。
9. 修复新版 Realms/精选服务器连接：
   - 保留 join 响应中的 `NetworkProtocol`，不再把 `NETHERNET_JSONRPC` 的 GUID 当作 RakNet `host:port`
   - 新增 `/ws/v1.0/messaging/connect` JSON-RPC 信令，支持区域节点、TURN 凭据、双层 WebRTC 消息、服务端 ACK 与 5 秒心跳
   - 部分 Realm 区域没有对应的 signaling DNS 记录；区域节点返回 NXDOMAIN 时自动改用全局 signaling 节点，并为重试生成新的会话/请求 ID
   - Realms 使用完整 ICE candidate SDP（禁用 trickle ICE），NetherNet 拨号只传裸 Network ID，不传界面内部前缀
   - NetherNet WebRTC 请求使用与 Minecraft 登录相同的 P-384 私钥和多人会话令牌生成 `a=identity`；身份提供方从 discovery 的授权 issuer 读取并保留原版要求的尾斜杠，避免 Realm 以错误码 37 拒绝匿名连接
   - 同步修复旧 Franchise signaling 的 opaque Network ID、凭据等待与初始化条件
10. 修复 Realm 登录阶段的两个后续问题：
   - NetherNet 拨号端会等待 Reliable/Unreliable DataChannel 都收到 DCEP 打开确认后才把连接交给 Minecraft 层，避免首个 `RequestNetworkSettings` 在通道仍为 Connecting 时丢失
   - 代理资源包握手兼容服务端发送的 `UUID_version` 标识；客户端内置的 1.26.40 基础包不再重复请求或转发，本次不增加材质包转换功能
   - 服务端发送空文本 Disconnect 时保留 wire reason 数字，不再退化为无法定位的 `use of closed network connection`

## Windows 构建

在源码目录使用 Go 1.27：

```powershell
$env:GOTOOLCHAIN = "local"
go build -buildvcs=false -trimpath `
  -ldflags "-s -w -X github.com/bedrock-tool/bedrocktool/utils.Version=v26.44-adapted -X github.com/bedrock-tool/bedrocktool/utils.CmdName=bedrocktool" `
  -o bedrocktool-v26.44-windows-amd64.exe ./cmd/bedrocktool
```

## 原始仓库限制

`subcommands/resourcepack-d/resourcepack-d.go` 在用户提供的源码中是 git-crypt 密文（以 `GITCRYPT` 标头开头），没有解密密钥时不能被 Go 解析。主程序没有导入这个独立包，因此不影响本次 Windows CLI 构建；但直接执行未经排除的 `go test ./...` 会在枚举该目录时报告 `unexpected NUL in input`。

原仓库的 `utils.TestInvalidJsonFix` 依赖旧版 HuJSON 对非法前导零的宽松解析，在当前锁定依赖下仍会失败；这不影响生产包编译或 26.44 协议适配，因此没有改变该无关逻辑。
